# 交易网关说明（OKX / 币安）

> 本文写于 **2026-10-09**。涉及"已核实"的部分都标了核实方式；币安侧当天已在香港
> 出口 IP 下做完真实小额闭环实测，结果见第 6 节（哪些已验证、哪些还没有，都写明）。

## 1. 一句话

下单能力被抽成**一个网关接口**，两个交易所各一个实现：

| 交易所 | 执行层 | 行情数据源 | 状态 |
|---|---|---|---|
| OKX | `pa_agent/trading/okx_trader.py` | `pa_agent/data/okx_source.py` | **实盘运行中**（已在真钱上跑） |
| 币安 | `pa_agent/trading/binance_trader.py` | `pa_agent/data/binance_source.py` | 代码就绪 + 单测通过 + **2026-10-09 真实小额闭环实测通过**（第 6 节） |

切换只需要改一个配置：`config/settings.json` 里的 `trading.venue`（`okx` / `binance`），
或者用菜单 **「交易设置（OKX / 币安）」** 里的下拉框。行情数据源是另一个下拉框
（`general.last_data_source`），两边**互相独立**——想用币安下单 + OKX 看盘是可以的，
但一般应该配套。

## 2. 统一在哪一层（2026-10-09 核实）

两个网关共用同一套**风控核心**，这部分不是复制粘贴，是同一份代码：

| 能力 | 出处 | 说明 |
|---|---|---|
| `plan_order()` 以损定量 | `okx_trader.py`（经 `gateway.py` 再导出） | 用入场价与止损价的距离反推下单量 |
| `evaluate_guard()` 风控闸门 | 同上 | 开关/凭据/置信度/持仓上限/日亏熔断 |
| `OrderPlan` / `ExecutionResult` / `GuardResult` | 同上 | 计划与结果的数据结构 |
| `ORDER_TAG = "PAAGENT"` | 同上 | "只撤自己下的单"的标记 |

入口函数只有一个：`pa_agent/trading/gateway.py::create_trader(settings)`，
按 `trading.venue` 返回对应网关。界面里 6 处下单/查状态的地方全部走它
（`main_window.py`），所以加第三个交易所时这些地方都不用动。

**两个网关都只认一种品种写法**：本项目的规范形式 `BASE-USDT-SWAP`
（`BTC-USDT-SWAP`）。币安的 `BTCUSDT` 只在网关内部换算
（`gateway.to_venue_symbol` / `to_canonical_symbol`），这样监控列表、记录文件、
图表缓存两边共用一份，不用改。

> 历史包袱：风控核心物理上还住在 `okx_trader.py` 里，`gateway.py` 只是再导出。
> 等币安在真实网络上跑通、有测试托底，再把它搬进 `trading/core.py`。
> 现在不动，是为了不碰正在实盘运行的下单路径。

## 3. 两个交易所的**机制差别**（这段最关键）

### 3.1 止损怎么挂

| | OKX | 币安 |
|---|---|---|
| 机制 | 下单时用 `attachAlgoOrds` 把止损**附着在订单上** | 没有这个机制，只能下**独立的**条件单 |
| 接口 | 与入场单同一个请求 | **必须走 Algo Order API**（`/fapi/v1/algoOrder`）。老接口报 `-4120 Order type not supported for this endpoint`（2026-10-09 实测） |
| 字段名 | `slTriggerPx` | `triggerPrice`（**不是** `stopPrice`）、`algoType=CONDITIONAL`、`clientAlgoId` |
| 挂单未成交时 | 止损已存在，成交后自动生效 | 止损**不存在**，必须等成交后由程序补挂 |
| 已有持仓的要求 | — | 币安要求**先有仓位**才能挂 `closePosition` 条件单，否则回 `-4509`（实测确认） |
| 程序崩在成交瞬间 | 止损仍然有效 | ⚠️ **仓位是裸的**（这是我们补不了的窗口） |

币安侧的应对（`binance_trader.py`）：

1. 下单后立刻查成交状态；**已成交 → 马上补挂** `STOP_MARKET`（优先 `closePosition=true`
   整仓保护，失败退回 `reduceOnly` + 数量，见 `place_stop`）。
2. 没成交 → 把"打算挂在哪"写进 `records/trading_stop_intents.json`。
3. 多品种监控每轮都会调 `ensure_stops()`：发现有持仓、没有止损、但有意图记录 →
   **自动补挂**；没有意图记录 → 日志告警让你手动处理。

⚠️ 第 2 步到第 3 步之间（正常 ≤1 分钟）以及"程序正好崩在这个窗口"，是币安机制带来的
**真实风险**，不是实现偷懒。真要在币安跑重仓，建议同时在币安 App 里手工挂一道保护。

### 3.2 其他差别

| | OKX | 币安 |
|---|---|---|
| 签名 | `base64(hmac_sha256(secret, ts+method+path+body))` | `hex(hmac_sha256(secret, query_string))` |
| 凭据字段 | api_key / secret_key / **passphrase** | api_key / secret_key |
| 参数位置 | 签名串在 header，body 是 JSON | 所有参数都在 query string |
| 时间戳 | ISO8601 毫秒 | 毫秒；偏差超 `recvWindow` 报 -1021 → 程序**自动对时重试一次** |
| 模拟盘 | 请求头 `x-simulated-trading: 1` | 换域名 `testnet.binancefuture.com` |
| 持仓模式 | `posSide: net` | **只支持单向持仓**；账户是双向（hedge）直接拒单 |
| 品种代码 | `BTC-USDT-SWAP` | `BTCUSDT`（内部换算） |

## 4. 配置

`config/settings.json` 的 `trading` 段新增字段（2026-10-09 核实）：

| 字段 | 默认 | 说明 |
|---|---|---|
| `venue` | `okx` | `okx` / `binance`；认不出的值一律回落到 okx |
| `credentials_path` | `config/okx_trading.json` | OKX 老字段，继续认 |
| `okx_credentials_path` | 空 | 想显式指定 OKX 凭据文件时用；留空沿用上一个 |
| `binance_credentials_path` | `config/binance_trading.json` | 币安凭据文件 |
| `okx_proxy` | 空 | OKX 专用代理 |
| `binance_proxy` | 空 | 币安专用代理 |

**凭据优先级**：环境变量 > 凭据文件。OKX 用 `OKX_API_KEY` / `OKX_SECRET_KEY` /
`OKX_PASSPHRASE`；币安用 `BINANCE_API_KEY` / `BINANCE_SECRET_KEY`。
两个凭据文件都已在 `.gitignore`（2026-10-09 补上币安那条）。

### 代理为什么按交易所分开配

两家的出口要求可能冲突，实测（2026-10-09）：

- 本机直连币安 `fapi` → **超时**（网络层不可达）
- 走现有代理（出口 `67.230.161.21`，美国洛杉矶）→ 币安返回 **451 地区封锁**
- 而 OKX 的 API Key 白名单**恰好绑在这个美国 IP 上**

所以代理要分开：优先级 `settings.trading.<venue>_proxy` → 环境变量
`PA_OKX_PROXY` / `PA_BINANCE_PROXY` → 系统 `HTTPS_PROXY`。

## 5. 怎么切到币安（操作步骤）

**代理钉死（2026-10-09）**：`run_pa_agent.sh` 把交易与行情流量**固定**走
`PA_PROXY_URL`（默认 `http://127.0.0.1:10808`），并导出 `PA_BINANCE_PROXY` /
`PA_OKX_PROXY` / `HTTP(S)_PROXY` / `ALL_PROXY` —— **不读电脑当前的网络/系统代理设置**。
实测：把代理指向死端口时行情立刻失败（说明不会静默回退到直连）。
换节点只改 `PA_PROXY_URL` 一处。⚠️ 固定的是"走哪个代理"，**出口 IP 仍由代理客户端决定**
（今天实测已在 美国 LA / 香港 / 美国 之间漂过），OKX 的白名单仍会因此掉线。

**运行方式（2026-10-09）**：`run_pa_agent.sh` 默认**后台无界面**运行
（`QT_QPA_PLATFORM=offscreen`，不会弹窗口）；要看界面用
`PA_AGENT_HEADLESS=0 ./run_pa_agent.sh`。

⚠️ 实测（2026-10-09，空闲态）：带窗口 **74 MB** / 后台无界面 **102 MB** ——
**offscreen 不省内存**，只是不显示窗口（Qt 的窗口树照样要建）。真想省内存需要
真正的无 Qt 后台模式（把监控循环从 GUI 线程里抽出来），目前还没做。

1. 币安 → **API 管理** → 创建 API Key：勾「启用合约」；**不要勾提现**；
   记下 API Key / Secret Key（币安没有 passphrase）。
2. 菜单 **「交易设置（OKX / 币安）」** → 交易所选「币安」→ 填两项 → **测试连接**
   （这一下会真的去读余额；连不上多半是网络出口问题）。
3. 先在 **测试网** 跑：`trading.simulated = true`（界面上选「模拟盘」）。
4. 行情数据源下拉框切到 **「币安」**（否则图表还是 OKX 的价，分析结果会错位）。
5. 确认无误后再切实盘，并勾选实盘风险确认。

## 6. 币安侧实测记录（2026-10-09，香港出口 IP）

网络一换到香港出口（`156.238.244.247`），币安 `fapi` 立刻可用。当天做了**三次真实小额
闭环测试**（SOL 永续，名义额 5.5 USDT，总计成本 **0.019 USDT**），结论：

**已核实可用** ——

- 签名、时间戳、`recvWindow` 都没问题（自动对时生效，没出现 `-1021`）
- `POST /fapi/v1/order` 市价开仓正常成交
- **止损改走 Algo Order API 后成功挂上**：`STOP_MARKET` / `side=SELL` /
  `triggerPrice=108.72` / `closePosition=true` / `clientAlgoId` 带 `PAAGENT` 标记，
  能在 `/fapi/v1/openAlgoOrders` 里查到
- 撤销条件单返回 `{"algoId":…,"code":"200","msg":"success"}`
- 平仓后**零残留**（0 持仓 / 0 条件单 / 0 普通挂单）——`close_position` 会先把
  **Algo 条件单一起撤掉**，否则那张旧止损会打掉下一次开的同品种仓位

**过程中发现并修掉的三个真问题**（都不是猜的，是实测撞出来的）：

1. **条件单迁移**：`/fapi/v1/order` 不再接受 `STOP_MARKET`（`-4120`），必须用
   `/fapi/v1/algoOrder`，且字段是 `triggerPrice` 而不是 `stopPrice`。
2. **`-4509`**：`closePosition=true` 的条件单**必须已有持仓**才能挂 —— 这反过来印证了
   "成交后才补挂止损"的设计是对的。
3. **两个解析/判定 bug**：`DELETE /fapi/v1/allOpenOrders` 成功时返回 `code:200`，
   被原来的"非 0 即错"判定当成失败，导致平仓中断；`equity_usd()` 误用
   `/fapi/v2/balance`（里面**没有** `totalMarginBalance`，实际取到的是
   `availableBalance`，一开仓就变小）。

**仍未验证**（真要用重仓前应该补）——

- 止损**触发**时的真实行为（这次只是把止损挂上又撤掉，没有让它打到）
- 限价入场单成交后由 `ensure_stops` 补挂的路径（这次走的是市价单即时成交分支）
- 测试网（`testnet.binancefuture.com`）行为，以及它与实盘的差异
- 极端行情下 `STOP_MARKET` 的滑点

## 9. 兜底："有仓位必有止损"（2026-10-10 修）

实盘事故：US / ZK / BTC 三笔**限价单挂单成交后没有止损**——意图记录丢失，且品种从监控
列表轮换出去后就再没人核对。修法三条：

1. `ensure_stops()` 改为**以交易所真实持仓为准**（不再依赖意图文件或监控列表）；
2. 有持仓、**没有意图记录**时，按「每笔最多亏 max_loss_per_trade_usd」从开仓均价反推
   止损价**直接补挂**（不再只告警）；算不出安全距离（仓位过小）才告警；
3. 监控线程每轮**全量核对所有持仓**（节流 2 分钟一次），不再"谁的结果回来查谁"。

⚠️ OKX 侧仍是"只核对不补挂"（它的止损随订单托管，缺止损=手动开的仓），需要人工处理。

## 10. 止盈：固定 1:3（2026-10-10 加，2026-10-12 从 1:2.5 改成 1:3）

用户要求：**所有交易统一固定盈亏比，且自动挂止盈**；偶尔会手动提前离场。

- `trading.risk_reward_ratio = 3.0`：**覆盖 AI 给的止盈价**，按
  `止盈 = 入场 ± 3 × 止损距离` 重算（原引擎的止盈实际只到 RR≈1.0，
  这是"盈亏比偏低"的根源）。设 0 = 恢复用 AI 的目标价。
- `trading.attach_take_profit = true`：止盈一并挂到交易所——
  OKX 走 `attachAlgoOrds.tpTriggerPx`；币安走 Algo API 的 `TAKE_PROFIT_MARKET`。
- 币安侧：意图记录里存 `take_profit_px`。**注意**：2026-10-13 之前写的"限价单成交后
  由 `ensure_stops` 一并补挂止损与止盈"是**错的** —— 代码里只补了止损，止盈从没挂上过，
  已于 2026-10-14 修复（见第 14 节）。

## 14. 币安止盈从未挂上 + 成交后 2 分钟裸奔窗口（2026-10-14 修）

**用户报告**：看到一笔持仓没有带止损。

### 14.1 那个"没带止损"的真相：2 分钟窗口（不是 bug，但确实存在）

DEEP-USDT-SWAP 这笔（2026-10-14）：

| 时间 | 事件 |
|---|---|
| 20:02:16 | 程序挂限价买单（价 0.02355 / 止损 0.02306 / 止盈 1:3 = 0.02502） |
| 20:30:29 | 成交（`/fapi/v1/userTrades` 实证） |
| **20:32:11** | 看守定时器发现持仓无止损 → 补挂止损成功（触发价 0.02306） |

即**成交后有 1 分 42 秒是裸奔的**。根因：币安的 `closePosition` 条件单要求"已有持仓"，
否则报 `-4509`，所以**无法在挂单时提前附带止损**；只能靠每 120 秒一次的看守定时器
（`_trade_guard_timer`）事后补挂。历史实测的补挂延迟：IO 10 秒、SAFE 33 秒、
DEEP 102 秒、RED 138 秒（都 < 定时器周期 + 一次接口往返）。

> 想把窗口压到 30 秒以内，只要把 `_trade_guard_timer` 的 120000 改成 30000
> （每 30 秒一次持仓查询，代价可忽略）。**截至 2026-10-14 仍是 120 秒，未改。**

### 14.2 真 bug：限价单成交后，止盈从来没挂上过

`_place_protection()`（下单时立刻成交才走这条）会挂止损 + 止盈；但**限价单成交是后来
才发生的**，走的是 `ensure_stops()` —— 那条路径**只有挂止损的代码，没有挂止盈的代码**，
意图记录里的 `take_profit_px` 从头到尾没人用。

证据（2026-10-14 核实）：

- `logs/pa_agent.log` 里 **"止盈已挂" 出现 0 次**，"TAKE_PROFIT" 出现 0 次；
- DEEP 持仓时 `openAlgoOrders` 只有 **1 张**（`STOP_MARKET`），`openOrders` 为空 —— 没有止盈单。
- 也就是说：**此前所有"止盈"都是用户手动平的**（例如 10-13 的 RED +6.38、BLUR +1.03），
  不是程序按 1:3 挂出去的。10-13 的分析里我把 RED 那笔说成"1:3 规则的第一笔完整止盈"
  **是错的**，特此更正。

**改法**（`pa_agent/trading/binance_trader.py::ensure_stops`）：

- 把"有止损就跳过这个品种"改成**分别核对止损与止盈**：`_has_stop_order()` 与新增的
  `_has_take_profit_order()`（都查 Algo 条件单 + 普通挂单，类型用新增常量 `_TP_TYPES`）；
- 止盈价取意图记录的 `take_profit_px`，只在 `attach_take_profit` 打开且记录里确实有该价时
  才补挂（**兜底补挂的手动仓不会被动加止盈**）；
- 补挂成功写 `补挂止盈成功：<品种> 触发价 <价>`，失败写 `补挂止盈失败` 并不影响止损。

回归测试：`tests/unit/test_binance_gateway.py` 新增 4 条（补挂止盈、已存在不重复挂、
开关关闭时不挂、手动仓不加止盈）。全量单测 28 个失败（上游基线），无新增。

### 14.3 451（地区限制）曾被当成"成功响应"（2026-10-18 修）

2026-10-18 06:22 起代理出口 IP 变成 `67.230.161.21`（美国），币安对公开接口和私有接口
统一返回 **HTTP 451**。451 的响应体是 `{"code": 0, "msg": "Service unavailable from a
restricted location..."}` —— **code 是 0**，旧 `_parse()` 认为"有 code 就是业务错误、返回给
上层处理"，于是把这个 dict 当成功结果返回；上层 `positions()` 把它当列表迭代，
炸成 `'str' object has no attribute 'get'`，**真正的 451 原因被完全掩盖**。

改法（`binance_trader.py::BinancePrivateClient._parse`）：非 200 且 code ∈
{None, 0, 200} → 直接抛 `BinanceTradeError("币安 HTTP 451: …（该出口 IP 被地区限制，
需要换代理节点）")`；`code=-1021`（时间戳过期）这类业务错误仍原样返回，保留
"对时后重试一次"的逻辑。

回归测试：`test_private_parse_raises_clear_error_on_451_region_block`、
`test_private_parse_keeps_business_error_for_timestamp_retry`。

> 网络本身要由用户处理：程序固定走 `PA_PROXY_URL=http://127.0.0.1:10808`，
> 出口节点由代理客户端决定；节点换成币安允许的地区后，程序会在下一轮（≤2 分钟）
> 自动恢复读取持仓、补挂止损止盈。

## 11. 自动下单日志带品种名（2026-10-12 修）

起因：10-12 复盘"今天错失的机会"时发现，日志里只有
`自动下单未执行：置信度 45 低于门槛 50`，**没有品种名**——当天 21 笔被卡掉的计划
只能靠 `records/pending/` 的 JSON 反推是哪一笔。

改法（`pa_agent/gui/main_window.py`）：

- `MainWindow.trade_finished` 信号由 `(结果)` 改成 `(结果, 品种)`，两条 emit 路径
  （`_maybe_auto_execute_watch` 的监控自动下单、`_send_order_async` 的手动/自动执行）
  都带上品种；
- `_on_trade_finished` 把品种写进日志，形如
  `自动下单未执行：PLUME-USDT-SWAP 置信度 45 低于门槛 50`；
  `自动下单成功：…` / `自动下单失败：…` 同样带品种，状态栏文案也一致；
- 顺带补上两条原来**只写状态栏、不写日志**的路径：`_execute_order()` 里的
  `TradeRejected`（闸门拒单）与"预演无计划"（`preview.plan is None`），
  在非交互（自动）模式下也写 `logger.warning`。

回归测试：`tests/unit/test_auto_trade_log_symbol.py`（信号签名 2 参、未执行日志带品种、
成功日志带品种）。全量单测仍是 28 个失败（上游基线），无新增——2026-10-12 核实。

## 12. 过期挂单全量清理 + 2 分钟看守定时器（2026-10-12 修）

**事故**：IO 的限价单 13:44 挂出（入场 0.187 / 止损 0.1786 / 风险 2 USDT），
按当日设置 `pending_entry_expiry_bars=4`（4 根 30m = 2 小时）应该在 15:44 作废
（该值已于当晚按用户要求改回默认的 **8 根，且不做周期换算**：30m 周期下就是 4 小时）。
但 IO 在 14:13 那轮动态换榜时被**轮出监控列表**，之后没有它的分析结果回来，
`_expire_stale_entries()` 再也没被触发 —— 那张单一直挂着，**16:16:38 成交**，
18:17 止损，实亏 −2.07 USDT。当天日志里没有任何一条"已撤掉过期入场挂单"。

根因和 2026-10-10 的裸奔事故一样：清理动作挂在"某个品种的结果回来"这条路径上，
品种一旦轮出监控列表就没人管。那次只修了止损，没修挂单过期。

**改法（两处，和 `ensure_stops` 同一套路）**：

1. `cancel_stale_entries(inst_id=None, …)` 支持**全账户扫描**：两个网关都改成
   按**每张挂单自己的 `instId`** 去撤（原来撤单时传的是外层 `inst_id` 参数，
   全账户模式下会传成 `None` 而撤不掉）。仍然只动带 `PAAGENT` tag 的入场单，
   止损/止盈单和手动单不碰（`okx_trader.py` / `binance_trader.py`）。
2. 主界面新增**交易看守定时器** `_trade_guard_timer`（120 秒），回调
   `_on_trade_guard_tick()` 做两件事：`_ensure_stops()`（补挂止损体检，
   全账户）与 `_expire_stale_entries()`（过期挂单清理，`inst_id=None` 全账户）。
   两个方法各自内部按 2 分钟节流、并自行判断"下单是否开启"，定时器本身空转无害。
   分析结果回来时仍会各触发一次（不依赖定时器）。

**效果**：挂单最长存活时间从"2 小时 + 无限期（取决于是否还在监控列表）"收敛到
**2 小时 + 最多 2 分钟**；IO 那笔单在 15:46 左右就会被撤掉，不会成交。

回归测试：`tests/unit/test_trade_guard_tick.py`（定时器在跑、tick 用 `inst_id=None`
扫全账户、2 分钟内不重复扫）、`test_binance_gateway.py` 与 `test_okx_trader.py` 各一条
全账户撤单用例（两个品种的单各按自己的品种撤）。全量单测 28 个失败（上游基线），
无新增——2026-10-12 核实。

## 13. 止损不可被程序改写；盈亏比上限取消（2026-10-12 用户要求）

**旧行为（上游自带）**：`util/trade_metrics.py` 里
`MIN_RISK_REWARD_RATIO = MAX_TP1_RISK_REWARD_RATIO = 1.0` —— 盈亏比必须**正好 1:1**。
AI 若算出 RR > 1（例如 RSR 那笔 2.55），程序**不动止盈**，而是把**止损往外撑**
直到 RR = 1.0。RSR 的结构止损 0.002265（2.79%，在 K4 摆动低点下方 1 跳）
因此被撑成 0.002164（7.12%）；这一步只写 debug 日志，**在日志文件里看不见**。

叠加当时的 1:2.5 止盈后更荒谬：程序撑出来的"新止损"恰好等于 AI 原来的止盈位，
2.5 倍止盈再基于新止损算一遍 —— 等于把 AI 设计的整笔交易**放大 2.5 倍**
（止损 2.79%→7.12%、止盈 7.12%→17.8%，盈亏比又回到 2.5），而 AI 原本的 2.55:1
跟我们想要的 2.5 本来就几乎一致（0.002496 vs 0.0024925，差 0.14%）。

**用户定下的三条规则**：

1. **AI 决定的止损位置一定不能变** —— 一个字都不改；
2. **每笔亏损金额由仓位大小控制** —— 以损定量（`max_loss_per_trade_usd`，当前 2 USDT）
   照旧，止损越宽仓位越小；
3. **止盈默认 1:3**，用户有时会手动提前平仓，其余不管。

**改法**：

- `MAX_TP1_RISK_REWARD_RATIO` 由 `1.0` 改为 `None`（无上限）；
  `widen_stop_for_tp1_rr_cap` / `adjust_decision_stop_for_tp1_rr_cap` 默认
  **原样返回止损**（要复现旧行为得显式传 `cap=1.0`，仅供测试）。
- `ai/stage2_normalizer.py` **删掉了调用点** —— 分析结果里的 `stop_loss_price`
  现在就是模型写的那个数（除突破单 entry 的 ±1 跳校正外，程序不再动价）。
- `trading.risk_reward_ratio` 由 `2.5` 改成 `3.0`（`settings.py` 默认值同步改）。
- 提示词同步改（`ai/prompt_assembler.py`、`ai/decision_stance.py`）：
  告诉模型"止损不会被程序改写、盈亏比没有上限、止盈由程序按 1:3 覆盖"。
- 每个可执行计划仍在日志里记一条 `计划止损宽度：… N×ATR`（第 12 节/第 7 节引用的
  ATR 度量），便于事后核对止损到底放在哪。

**没有跟着改的**：`prompt_engineering/二元决策.txt` 里"向外扩 stop 时不得超过尖峰
高度 50%"这类句子保留了 —— 它现在既不会被程序执行、模型也被禁止自行扩 stop，
属于失效但不误导的残留（改上游教材文本风险更大）。

回归测试：`test_trade_metrics.py`（上限为 None、默认不动止损、显式 `cap=1.0` 复现旧行为）。
全量单测 28 个失败（上游基线），无新增——2026-10-12 核实。
